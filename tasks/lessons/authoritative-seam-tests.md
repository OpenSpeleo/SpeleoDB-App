# Test the Authoritative Seam

## Lesson

A regression test proves a behavior only when it exercises the production seam
that owns that behavior. A test against a retired helper, a duplicate algorithm,
or a mock preconfigured to return the desired state can pass while the real
storage, concurrency, or UI path remains unsafe.

## Rules

1. Trace the production call path before writing the regression test. Identify
   the method and awaited boundary that actually owns the invariant.
2. For IndexedDB atomicity, schema parsing, migrations, and restart behavior,
   use fake IndexedDB with the real repository/store transaction. A mocked
   service method cannot prove transaction ordering or conditional replacement.
3. For cancellation and races, defer the real injected dependency at the exact
   await being audited (cache read, write, delete, fetch, retry sleep). Assert
   operation ordering and final durable/runtime state, not just callback counts.
4. For revision-driven React state, trigger the controller/context revision and
   accessor used by the mounted component. Do not mutate a test-only state copy
   or call an obsolete data-only accessor.
5. For shared ownership, include both unique and shared resources and cover the
   queued and active cases. Prove sole-owner cancellation and remaining-owner
   continuity separately.
6. Keep adversarial fixtures independent from implementation helpers when the
   helper itself is under test. Expected geometry, metadata, or counters must
   not be generated by the same code that produces the actual value.
7. Compilation is not runtime evidence. Record physical-device verification
   separately for WebView responsiveness, native modal dismissal, real network
   behavior, device logs, and persistence across force-quit.

## Review question

Before accepting a regression test, ask: “If the production transaction, await
ordering, or mounted consumer were broken while this mock/helper stayed
unchanged, would the test fail?” If not, move the test to the authoritative
seam.
